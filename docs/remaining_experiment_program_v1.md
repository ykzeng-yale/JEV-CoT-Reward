# Remaining experiment program, version 1

**Date:** September 29, 2026
**Purpose:** one end-to-end decision plan for the remaining JEV-CoT-Reward research. This is a preregistration scaffold and execution queue, not a claim that the proposed studies are already valid or that any controller works.

## Scientific bottleneck and current decision

The bottleneck is **task/action validity and claim identification**, not raw GPU capacity. The candidate screen currently has zero families passing all requirements: sufficient natural checkpoints, an action that changes downstream state, an independent terminal outcome, a compatible strong baseline, an honest total-cost comparison, a held-out transfer design, and a residual contribution after prior-art review. Jev-dependent work also remains on hold pending written TypeSafe clarification for the specific research, retention, analysis, and release uses.

Therefore the program is staged, but not a succession of arbitrary tiny model pilots. The already-submitted InterWhen adaptation is the only live inference job. It is a published-baseline/runtime adaptation on Game24, not a Jev efficacy study and not a method novelty test. While it queues, only independent contract/data/code review and the complete experiment plan are actionable. Do not start another model job until the task/action and permission gates below pass.

## Power and compute plan

The future confirmatory unit is the **independent task**, not model calls, branches, repeated seeds, or checkpoints. Use paired same-task outcomes only where task cloning and common randomization are valid. Let the per-task paired difference be `D ∈ {-1,0,1}`, mean `δ`, and discordance probability `p_d = P(|D|=1)`. A normal planning approximation is

\[
n \approx \frac{\left[z_{1-\alpha/2}\sqrt{p_d}+z_{1-\beta}\sqrt{p_d-\Delta^2}\right]^2}{\Delta^2}.
\]

Using 80% power, two-sided α=.05 and the previously proposed practical target Δ=3 percentage points gives:

| Planning discordance | Independent tasks for 3 pp | Tasks if six contrasts were all co-primary | Tasks for 5 pp, single primary |
|---:|---:|---:|---:|
| 16.7% (observed GUARD–random development estimate) | 1,455 | 2,245 | 522 |
| 30% (conservative planning scenario used in prior design) | **2,614** | 4,034 | **940** |

These are planning approximations, not guarantees. The 16.7% rate is from a different development controller/task, so the prespecified plan uses 30% sensitivity unless a blinded, outcome-independent variance estimate on the selected task family supports a revision. Predeclare **one** primary contrast; avoid paying the six-primary penalty by making every arm co-primary. Use cluster bootstrap/paired randomization inference for final intervals and account for task-family clustering. If the desired minimal effect, plausible discordance, or task-level dependence changes, recompute before freezing the test set.

For rough resource sizing only, the audited four-arm CUDA v4 run used 1.5603 GPU-hours for 96 tasks: about 0.01625 GPU-hours/task. Linear extrapolation to 2,614 tasks is about **42.5 GPU-hours** for a v4-like four-arm workload. This is not a runtime prediction for CLI trajectories; long contexts, environment actions, retries, timeout tails, more arms, and different runtime can raise it substantially. First profile an already qualified task on one GPU using development-only tasks; then size one bounded Slurm batch and parallelize across independent workers only if actual memory/throughput supports it. Do not reserve B200/H200 capacity just because it exists. Pending time is zero GPU-hours.

## Cost ledger and inference fairness contract

Every run must report per arm and aggregate: model/revision/dtype/runtime; task and episode counts; generated and discarded tokens; prompt/prefill tokens; judge/controller calls and billed judge usage; tool/test calls; wall/serial latency; timeouts and unfinished episodes; GPU allocation elapsed-hours; failed/retried work; exact model and task hashes. Count shared prefixes once at collection level but do not hide them from total study cost. Present both matched-budget outcome comparisons and the unmatched operational costs. Keep Jev spend cumulative under the existing $25 cap; no Jev job is allowed until the written-terms prerequisite is met. Local judges must be independently designed, not distilled from Jev outputs.

## Pre-run checklist (all required before an efficacy submission)

1. Immutable public task/tag/revision, license, train/development/untouched-test split, and no benchmark leakage into model/controller training.
2. Natural-prefix sampling rule and eligible-checkpoint definition fixed without viewing judge decisions or terminal labels.
3. One executable action, frozen continuation policy, exact intervention/sham semantics, and a prior-art paragraph showing what is different empirically.
4. Independent terminal evaluator, tamper tests, environment reset/clone tests, and task-level statistical unit.
5. Strongest compatible published baseline pinned and adaptation/reproduction status accurately labeled.
6. Fixed model/tokenizer/runtime/prompt/sampling/seed/context, wall-clock, tool, token and timeout budgets.
7. One primary contrast, practical effect threshold, sample size, interval/inference method, subgroup and multiplicity policy frozen.
8. Total-cost ledger and Jev cumulative spend estimate; written TypeSafe clarification for exact Jev use, retention, publication and derived-controller activity.
9. Frozen evaluation manifest and audit scripts hashed before outcomes; preserve the closed v1 test.
10. Current host/account/queue/quota check, bounded immutable run directory, and no duplicate live job.

## Claim policy

This project has **not** established a methods-level novelty gap, positive action utility, Jev incremental value, OOD transfer, long-horizon exploration benefit, or scientific discovery. Positive, null, and negative findings are all valid. Infrastructure compatibility and published-baseline adaptation are not efficacy. If no candidate survives E1 and prior-art review, the scientifically correct result is a documented no-go or a narrower benchmark audit—not an unsupported claim or an arbitrary GPU run.
