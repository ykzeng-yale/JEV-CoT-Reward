## Power and compute plan

The future confirmatory unit is the **independent task**, not model calls, branches, repeated seeds, or checkpoints. Use paired same-task outcomes only where task cloning and common randomization are valid. Let the per-task paired difference be `D ∈ {-1,0,1}`, mean `δ`, and discordance probability `p_d = P(|D|=1)`. A normal planning approximation is

\[
n \approx \frac{\left[z_{1-\alpha/2}\sqrt{p_d}+z_{1-\beta}\sqrt{p_d-\Delta^2}\right]^2}{\Delta^2}.
\]

Using 80% power, two-sided α=.05 and the previously proposed practical target Δ=3 percentage points gives:

| Planning discordance | Independent tasks for 3 pp | Tasks if six contrasts were all co-primary | Tasks for 5 pp, single primary |
|---:|---:|---:|---:|
| 16.7% (observed GUARD–random development estimate) | 1,455 | 2,245 | 522 |
| 30% (conservative planning scenario used in prior design) | **2,614** | 4,034 | **940** |

These are planning approximations, not guarantees. The 16.7% rate is from a different development controller/task, so the prespecified plan uses 30% sensitivity unless a blinded, outcome-independent variance estimate on the selected task family supports a revision. Predeclare **one** primary contrast; avoid paying the six-primary penalty by making every arm co-primary. Use cluster bootstrap/paired randomization inference for final intervals and account for task-family clustering. If the desired minimal effect, plausible discordance, or task-level dependence changes, recompute before freezing the test set.

For rough resource sizing only, the audited four-arm CUDA v4 run used 1.5603 GPU-hours for 96 tasks: about 0.01625 GPU-hours/task. Linear extrapolation to 2,614 tasks is about **42.5 GPU-hours** for a v4-like four-arm workload. This is not a runtime prediction for CLI trajectories; long contexts, environment actions, retries, timeout tails, more arms, and different runtime can raise it substantially. First profile an already qualified task on one GPU using development-only tasks; then size one bounded Slurm batch and parallelize across independent workers only if actual memory/throughput supports it.
